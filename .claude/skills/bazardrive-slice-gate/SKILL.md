# Срез BazarDrive: от задачи до мержа

## Порядок задач
1. Порядок — только критический путь BD-STATUS (#1145), сверху вниз. Задачу вне списка не брать без «да» владельца.
2. Код — только в одной задаче. Следующую не начинать, пока текущая не смержена и её issue не закрыт.
3. Пока текущая ждёт ревью — только подготовка следующей: аудит (read-only) и вопросы Р1…Рn. Без веток и кода.
4. В шапке BD-STATUS всегда строка «Сейчас в работе: #… — этап»; обновлять при каждой смене этапа.

## Порядок среза
Аудит → контракт/решения владельца → код → смоук + негатив-контроль на main (тест падает на старом коде) → живая проба main | ветка → bump sw.js VERSION (если public/ и precache) → node scripts/check.mjs, node scripts/check-precache-drift.mjs, node scripts/dispatcher.mjs (READY_CLEAN) → PR → ревью → мерж squash с --match-head-commit.

## Негатив-контроль
Перед подменой файлов на версию из main — резервная копия; возврат только из копии, не git checkout (теряет незакоммиченное).

## Ревью
- CodeRabbit: 1 ревью в час на весь репозиторий. Перед @coderabbitai review проверить локальную запись времени последнего запроса и историю репо за час (slot-cr). Опрос — раз на слот.
- Codex (@codex review) — только для высокого риска, параллельно с CodeRabbit. Лимит Codex — не ждать, отметить в итоге.
- Тред закрывать только после подтверждённого фикса. Замечания вне диффа — ответ комментарием.
- Однотипные находки «вариант свободного текста» — не чинить по одному: записать в issue как известное ограничение, ответить, закрыть.
- CodeQL: разобрать каждый новый алерт; настоящий — чинить; ложный — won't fix с объяснением.

## Мерж
- Высокий риск (server/, миграции, auth/роли, деньги, безопасность, CI): только после «ок» владельца.
- Низкий (public/ клиент, docs): самомерж при чистом CodeRabbit, 0 тредов, зелёном CI/check, READY_CLEAN; владельцу — короткий итог.
- Сомнение = высокий риск.
- После мержа: pull main, check, dispatcher, убрать стенды/worktree, обновить BD-STATUS (#1145).

## Секреты и данные
- TELEGRAM_BOT_TOKEN и другие секреты — только из server\.env владельца; не печатать, не логировать, не коммитить; в отчётах — только «есть/формат ок».
- Никаких личных данных владельца и пассажиров в репо (он публичный).
- Миграции на dev-БД применяет владелец: прислать команду (docker cp + psql -v ON_ERROR_STOP=1 -f).

## Экономия лимита
Отчёты 3–5 строк, опрос очереди раз на слот, ненужные фоновые задачи и стенды останавливать, приоритет — критический путь из BD-STATUS.

## Отчёт владельцу
По-русски, 3–5 строк: что смержено, что ждёт, что нужно от него (вопросы Р1…Рn с рекомендацией).
