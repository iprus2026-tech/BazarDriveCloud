## Key paths

### Guest

First-run welcome path: `/welcome` (empty hash default) → role select → permissions → directly to `/feed` (passenger) or `/driver-map` (driver). The welcome flow persists `welcomeSeen` and the selected role and **does not** route through `/onboarding?step=phone` — that route is the profile-side phone-verification re-entry path, not part of the first-run welcome transition. There is no separate `/auth` screen — phone verification lives inside the onboarding step host.

### Passenger

`/map` has two shipped branches and **handoff coverage must keep BD-MAP-02 visible** (it is a real registered screen):

- **my-location branch:** `/map` → my-location action → `/location-permission` (BD-MAP-02) → three split destinations: **allow → `/map?state=default`**; **manual → `/route-picker`**; **back → `/map`**.
- **choose-route / manual branch on the map:** `/map` → choose-route / manual route flow → `/route-picker`.

From `/route-picker` onward: `/route-picker` → `/route-preview` → `/order-map-draft` → «Разместить заявку» → `handlePublish` creates the order and re-renders the **success card with `lastOrder`** in place (submit does not navigate) → user taps the success CTA (`responses` / `my-order`) → `handleAction` navigates to `/responses?orderId=...&state=empty` (success state preserved through the handoff) → select-driver → `/active-ride?role=passenger&tripId=<tripId>&status=DRIVER_EN_ROUTE` (`buildPassengerActiveRide()` + `activeRideUrl()` navigate directly; **no `/trip-confirmation` hop** on this flow) → completion → history. There is no shipped passenger receipt screen — completion-screen receipt viewing is UI-only.

### Driver

`/profile?role=driver` → `/driver-map` → accept nearby order → accepted-order card (`STATE.ACCEPTED`) → «К поездке» → `/active-ride?role=driver&tripId=...&status=ACCEPTED` (the DriverMap CTA builds this URL; bare `/active-ride?role=driver` may fall into fallback / demo behavior) → completed earnings → driver history/payouts at `/profile?role=driver&pane=payouts` → receipt at `/receipt?tripId=...`.

### Shared

Feed, chat, rules, settings and notifications are shared surfaces and must not leak passenger/driver state across roles.

## Consistency notes

- Driver finance/receipt atoms should remain consistent with passenger receipt work.
- Passenger trip history already renders inside `/profile` and the active-ride completion path; the audit-gate scope is a dedicated `/history` route + parity loading/detail states only, not a from-scratch build.
- Map screens remain placeholder/foundation until a real map adapter lands.
- Auth is UI-only in this artifact; no SMS backend is implied.

- **BD-ERROR-01 / BD-ERROR-01A** — the runtime foundation is now Partial, not fully Missing. **01A** ships an app-shell singleton overlay (`public/src/app_error_overlay.js`, wired in `public/src/app.js`, `.bd-error-*` CSS in `public/styles/cloud.css`, precached by `public/sw.js`, guarded by `scripts/smoke-global-error-overlay.mjs`). It is driven imperatively via `window.BD.GlobalError.show(state, options?)` / `.hide()` over the five states (offline, server_error, timeout, retrying, recovered) and is **not a route** — there is intentionally no `/error` registration; it overlays the current screen rather than replacing it. The overlay is non-mutating: no ride/order/storage/backend/Mapbox writes, `onRetry` is a demo callback only. **BD-ERROR-01B** (`public/src/app_connection_status.js`) wires **only** the browser `online`/`offline` events to that overlay (offline → `show('offline')`, online → `show('retrying')` → short delay → `show('recovered')`); it does not handle fetch failures, backend retries, ride/Mapbox/GPS errors, or order/ride mutations. **BD-ERROR-01C-A** (`public/src/app_error_triggers.js`) adds a non-mutating adapter `reportAppShellError(kind, options)` that maps a flow's error kind (offline / timeout / server_error / retrying / recovered) to that overlay; while the device is offline (`navigator.onLine === false`) any valid kind is coerced to `offline`, and an unknown kind is a safe no-op (validated before the override). It is a **contract only** — not exposed on `window`, no `fetch` wrapping, and no SW fetch-handler change. **BD-ERROR-01C-B** is the first real flow trigger: `public/src/screens/feed.js` wraps its `listFeedPosts()` data load (`loadFeedPosts()`) in a try/catch that calls `reportAppShellError('server_error')` on failure and falls back to `[]`. It is a **defensive** wire — `listFeedPosts()` resolves from mock/localStorage and does not reject today, so the catch is dormant — but a future data-layer/backend failure routes through the global overlay instead of silently rendering an empty feed. The feed's own empty state is preserved (the overlay is additive, never a replacement). The overlay's «Повторить» button is wired via an `onRetry` callback that re-runs the load as a retry: it shows the non-blocking `retrying` progress state and dismisses the overlay **only after a successful reload**, and **only if the overlay is still that `retrying` state** (`dismissAppShellError({ onlyIfState: 'retrying' })`) so a newer state — e.g. an offline banner the connection watcher raises mid-retry — is not clobbered.
